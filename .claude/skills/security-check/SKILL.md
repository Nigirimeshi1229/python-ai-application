# セキュリティチェック

このアプリの安全性を確認し、**報告書と修正案**を出す。コードは、ユーザーが修正案を見て了承するまで変更しない。勝手に直すと、ユーザーが変更内容を把握できなくなるため。

## 前提（脅威モデル）

重要度を正しく付けるために、まずこのアプリの置かれた状況を押さえる。

- 利用者は本人1人だけ。データベースも認証も使わない。**この方針はプロジェクトで決まっているので、「ログイン機能を付ける」「DB で管理する」といった提案はしない。**
- 守るべきいちばん大事なものは **Gemini の API キー**。漏れると他人に使われて料金が発生する。
- 次に大事なのは、ユーザーが入力した文章（社内の情報が含まれうる）。
- 想定する攻撃者は「同じ社内ネットワークにいる人」「コードやファイルを見た人」「入力に紛れ込んだ悪意ある文章（コピペ元のメールや Web ページなど）」。インターネット全体からの攻撃は、localhost で動かしている限り想定しにくい。

この前提から外れた一般論（大規模サービス向けのレート制限、WAF、多要素認証など）は報告に含めない。ノイズが増えて本当に大事な指摘が埋もれるため。

## 手順

### 1. 機械チェックを実行する

```powershell
.\.venv\Scripts\python .claude\skills\security-check\scripts\scan.py .
```

秘密情報の直書き、`.gitignore`、`.streamlit/config.toml` の公開設定、`unsafe_allow_html` や `eval` などの危険な書き方、`requirements.txt` のバージョン指定を調べる。結果は手がかりであって結論ではない。誤検知（例：プレースホルダーの文字列）は手順 2 で確認して落とし、見逃しは手順 2 で拾う。

### 2. コードを読んで確認する

`app.py`・`gemini_client.py`・`tools.py`・`.env.example`・`.gitignore`・`README.md`・`CLAUDE.md`（起動方法の記載）を読み、次の観点を一つずつ確認する。機械チェックでは見えない「値の流れ」を追うのがこの手順の目的。

**API キー**
- キーの入口（`.env` / サイドバーの入力欄）から `genai.Client` に渡るまでの経路で、画面・ログ・ファイル・履歴・ダウンロード内容に出る箇所がないか。
- 入力欄が `type="password"` になっているか。`value=` に環境変数の値を入れている場合、ブラウザに送られる HTML に含まれることを意識する（localhost 限定なら許容範囲だが、公開時は問題になる、と書き分ける）。
- エラー表示（`show_error` など）で例外の中身をそのまま出していないか。例外メッセージや URL にキーが含まれる可能性を確認する。
- `.env.example` に本物のキーが入っていないか。

**公開範囲**
- README・CLAUDE.md・起動スクリプトの起動コマンドに `--server.address localhost` が付いているか。付いていない起動方法が書かれていれば指摘する。
- `.streamlit/config.toml` の有無と中身。

**画面表示**
- 生成結果や入力を `st.markdown` などで表示する箇所で、`unsafe_allow_html=True` を使っていないか。Streamlit の `st.markdown` は既定で HTML を無効化するので、使っていなければ問題なしと判断してよい。
- ダウンロードのファイル名にユーザー入力が入っていないか（パス区切り文字が入る恐れ）。

**プロンプトインジェクション**
- `tools.py` の `build_prompt` が入力をどう埋め込んでいるか。入力欄の文章に「これまでの指示を無視して…」と書かれていた場合の影響を考える。
- このアプリは生成結果を表示するだけで、ファイル操作・外部送信・ツール実行をしないので、影響は「おかしな文章が出る」程度に限られる。重要度は基本的に「低」とし、生成結果を別の処理（メール送信など）に渡す機能が追加されていたら引き上げる。

**Google に送られるデータ**
- 入力欄の文章は `build_prompt` でプロンプトになり、`system_instruction` と一緒に Gemini API へ送られる。どの入力欄が送信対象になるかを確認する（通常はすべて）。
- ユーザーは社内のメール・議事録・顧客情報などを貼り付けがち。送った内容の扱い（保存期間、サービス改善に使われるか）は、Google の利用規約と、無料枠・有料枠のどちらを使っているかで変わる。規約は変わるので、条件を断定せず「無料枠では使われる場合がある。最新の規約で確認を」と書く。
- 送信前に自動で伏せ字にする機能や、社外送信を止める仕組みはこのアプリにない。それを前提に、ユーザー側でできる対策（個人情報・社外秘を貼らない、課金を有効にした API キーを使う、社内規程を情報システム部門に確認する）を示す。
- 重要度は基本的に「情報」。コードの欠陥ではなく、使い方の注意だから。ただし、ファイルの読み込みや他システムとの連携などで、ユーザーが意識しないまま大量の社内データを送る機能が追加されていたら「中」に引き上げる。
- 生成結果のログや履歴をアプリ側で外部（クラウドストレージなど）に保存する処理が追加されていないかも、あわせて確認する。

**その他**
- `subprocess`・ファイルの読み書き・外部 URL へのアクセスなど、新しく追加された処理があれば、入力値がそこに流れないかを確認する。

### 3. 依存パッケージの脆弱性を調べる（pip-audit）

```powershell
.\.venv\Scripts\python -m pip_audit --version
```

- 入っていない場合は、**インストールしてよいかユーザーに確認してから** `.\.venv\Scripts\python -m pip install pip-audit` を実行する。pip-audit は PyPA（Python の公式パッケージ管理団体）のツールで、PyPI から入れる。
- 実行時はインターネット上の脆弱性データベースに問い合わせる。送るのはパッケージ名とバージョンだけで、コードや API キーは送られない。この点をユーザーに一言伝える。

```powershell
.\.venv\Scripts\python -m pip_audit -r requirements.txt
```

- 断られた場合やネットワークにつながらない場合は、この手順を飛ばし、報告書に「未実施」とその理由を書く。黙って省略しない。
- `pip_audit` を新たに入れても、アプリの動作には不要なので `requirements.txt` には追加しない。

### 4. 報告書を書く

重要度は次の基準で付ける。迷ったら「実際に起きたときの被害」と「起きやすさ」の両方で考え、根拠を一言添える。

| 重要度 | 目安 |
|---|---|
| 高 | API キーや入力内容が、本人以外に見られる・使われる状態になっている（直書き、git 登録、社内公開の設定など） |
| 中 | 条件がそろうと漏えい・不正表示につながる（エラーにキーが出うる、HTML をそのまま表示など） |
| 低 | 影響が小さい、または起きにくい（このアプリでのプロンプトインジェクションなど） |
| 情報 | 今は問題ないが、知っておくと付け忘れ・設定ミスを防げること |

書式は次のとおり。問題が見つからなかった観点も「確認済み」に書く。何を見て安全と判断したかが残っていないと、ユーザーはチェックの範囲を信用できないため。

```markdown
# セキュリティチェック結果

## まとめ
（全体の状況を2〜3文。高・中・低・情報の件数）

## 指摘事項
### [高] 見出し
- **場所**: `ファイル名:行番号`
- **問題**: 何が起きうるか（具体的に）
- **修正案**: 変更内容（短いコード例や差分）

（重要度の高い順に並べる）

## 確認済み（問題なし）
- API キー: …を確認し、問題なし
- …

## 依存パッケージ（pip-audit）
（結果、または「未実施：理由」）

## 次の一手
修正案のうち、どれを適用するかを聞く。
```

### 5. 修正する（ユーザーが了承した場合のみ）

- 了承された項目だけを直す。
- 変更後、CLAUDE.md の AppTest の手順で全ツールの画面がエラーなく表示されることを確認する。Gemini API を実際に呼ぶ確認はしない（料金がかかるため）。
- 起動方法や設定ファイルなど、使い方が変わる修正をしたら `README.md` も更新する。
- 何をどう変えたかを最後に報告する。

## 守ること

- **秘密の値を出力しない。** API キーなどを見つけても、報告書・コマンド・ログには先頭4文字＋伏せ字（`AIza********`）で書く。`.env` の中身を表示しない。存在とキー名の有無だけを確認すれば十分。
- 漏えいが疑われるキー（直書きされていた、git に登録されていた等）は、ファイルから消すだけでは不十分。Google AI Studio でキーを無効化して作り直すよう案内する。
- `git rm`、`git filter-repo`、ファイル削除、権限変更など、元に戻しにくい操作やシステムに関わるコマンドを修正案に含める場合は、「実行前に情報システム部門、または技術責任者のレビューを受けてください」と添える。
- アプリを起動して確認する場合は、必ず `--server.address localhost` を付ける。
